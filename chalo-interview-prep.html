Part A: understand the project

1. The 2-minute pitch

Chalo is a group-trip app for India. A group plans a trip, tracks every shared expense, keeps tickets and bookings in one place, shares photos that sort themselves, and turns those photos into Instagram-ready collages and reels.

Three ideas make it more than a Splitwise clone:

  • Fair tax sharing. On a restaurant bill, tax, service charge, tip and discount are shared in proportion to what each person actually ate, down to the paisa.
  • Offline first. Everything is written to the phone first and synced later, so a ticket opens in airplane mode and an expense added on a mountain road is not lost.
  • Private by design. Face matching runs on the device, only for members who opt in. No photo goes to a third-party AI service.

It runs entirely on free tiers (Supabase, Vercel, GitHub Actions). One TypeScript codebase ships as a PWA and as an Android APK through Capacitor. It was built milestone by milestone against a written specification, with each requirement tied to a test.

Flow 1: add an expense (works offline)

  1. The form validates input with Zod. packages/core computes shares with allocate(); the UI does no money arithmetic.
  2. The row is written to Dexie and an operation is appended to the outbox. The screen updates at once.
  3. When online, the sync engine drains the outbox into the save_expense RPC. The server checks that payers and shares sum to the total, then stores the row.
  4. Realtime pushes the change to the other phones.

Flow 2: sync pull

  1. On start, reconnect and focus, the client asks for rows with updated_at later than its last pull, per table and group, including soft-deleted rows as tombstones.
  2. A Realtime subscription per group delivers live changes between pulls.

Flow 3: photo upload and auto-tagging

  1. The browser resizes the image on a canvas and reads EXIF with exifr (time, optional location).
  2. The file goes to Supabase Storage; the row records the trip day and place.
  3. The uploader's device detects faces and compares them only with the fingerprints of members who consented. Unmatched face data is discarded immediately.

4. Data model and algorithms

  • Money is integers in paise. No floats anywhere. Intermediate products use BigInt.
  • allocate(total, weights) splits an integer exactly in proportion to weights and hands out the leftover paise deterministically, so the parts always sum to the total.
  • Balance = paid − owed + settlements paid − settlements received. Over all members the balances sum to exactly zero.
  • Simplify debts: repeatedly match the largest debtor with the largest creditor (ties by member id). At most n − 1 transfers.
  • Itemised bill algorithm (TAX-003):
    1. Spread discounts across items in proportion to item amounts.
    2. Split each item among its assignees by weight, tracked per tax class.
    3. Each person's total of items becomes their weight for sharing service charge, tip and untyped tax. A tax tied to a class uses only that class's amounts.
    4. Charges with allocation "equal" use weight 1 for everyone who has any item.
    5. Owed = items + charge shares. A breakdown is kept for "Explain my share".
  • UPI link: upi://pay?pa=…&pn=…&am=…&cu=INR&tn=…. The app records a payment only after the user confirms it went through.
  • Face match: cosine similarity of embeddings; accept the best match only if it passes the threshold and beats the second best by at least 0.05. Each member is tagged at most once per photo.
  • Conflicts: last write wins by server updated_at for most tables. Expenses carry a version; a stale one is rejected with VERSION_CONFLICT and the user chooses "Keep theirs" or "Apply mine on top".

6. The spec-driven process

  • A written specification (SPEC.md) defines requirement IDs, priorities (P0 to P3), milestones with a Definition of Done, and normative test vectors (Appendix A).
  • Per milestone: re-read the rows, write a plan in docs/PROGRESS.md, write core tests first, implement, run lint, typecheck, unit, property and SQL tests, deploy to staging, verify the DoD, then tag.
  • Commits are Conventional Commits that carry requirement IDs, for example feat(UX-004): …. A traceability test checks the IDs against the spec.
  • Where the spec was silent, the choice went into docs/DECISIONS.md; spec changes were proposed in docs/SPEC_CHANGES.md, never edited silently.
  • Stop-and-ask rules: new paid service, new personal data, face or location handling changes, a test vector that looks wrong, destructive production actions.

8. Deployment, security and privacy

  • Environments: separate staging and production Supabase projects; migrations are applied to both. Applied migrations are never edited.
  • Secrets: never committed; .env.example lists names only. The service-role key lives only as a Supabase secret, used by the single delete-account Edge Function.
  • Access control: Row Level Security on every table; writes go through RPCs that check the caller can write to the group.
  • Content Security Policy with no inline styles; extended only when needed ('wasm-unsafe-eval' for OCR, media-src blob: for reels).
  • Signed storage URLs expire within one hour.
  • Privacy: no analytics, ads or trackers; face data and photo location are separate optional consents; withdrawing deletes the fingerprint and all automatic tags; account deletion turns the member into "Former member" so balances stay valid. A plain-language privacy page follows India's DPDP Act 2023 intent and still needs a legal review before a public launch.

9. Hard problems and how they were solved

  • Paise that do not add up. Solved with integer money and one allocate() used everywhere, protected by property tests.
  • Two people editing one bill. Version check on the server and a "Review changes" screen instead of silent overwrite.
  • Offline tests flaking. The e2e suite waits for a readyForOffline signal before cutting the connection, and a scattered timeout is rerun alone before it is treated as a bug.
  • Capacitor plugin hang. Returning a plugin object from an async function made the promise never resolve, because plugins look "thenable". The code never returns a plugin from an async function.
  • Face accuracy without a real test set. The face code sits behind an interface, was verified with a stand-in model, and ships a tuning procedure and debug screen (docs/FACE_TUNING.md).
  • Reels in the browser. Canvas plus MediaRecorder, choosing MP4 or WebM by isTypeSupported, with a lazily loaded FFmpeg WebAssembly fallback.
  • Free-tier pausing. A scheduled keep-alive workflow.

10. Limitations and next steps

  • Face threshold (0.90) is a placeholder until it is tuned on real photos in low light and varied skin tones.
  • OCR accuracy on crumpled receipts is unverified.
  • Android share sheet, reminders and Spotify links are manual checks on a real phone.
  • iOS has no native app, only the installed PWA.
  • Supabase free limits (about 500 MB database, 1 GB storage) cap photo volume; the storage guard warns before the limit.
  • Next: privacy review before launch, Instagram direct publishing for professional accounts (P3, not started), more languages.

Product and users

★ Give me the 2-minute pitch.

Chalo is a group-trip app for India. It tracks shared expenses with fair tax splitting, keeps tickets and bookings available offline, sorts a shared photo album by person, place and day, and builds Instagram collages and reels. It runs on free tiers only, as a PWA and an Android app from one codebase.

Follow-up: Which part was hardest? The itemised bill: tax and discounts must be shared fairly and add up to the paisa, under every input order.

★ Who is it for and what problem does it solve?

Friend groups travelling in India. Today they juggle a spreadsheet, WhatsApp for tickets and a Google Drive for photos. Splitwise cannot share GST and service charge by what each person ordered, and nothing links expenses, plans, tickets and photos.

Follow-up: Why not just use Splitwise? It lacks proportional tax sharing, offline tickets, face-sorted photos and UPI settle-up in one place.

What are the non-goals?

Moving money, auto-posting to Instagram, booking tickets, in-app chat and anything that costs money. Chalo records settlements and opens the user's UPI app; it never holds funds.

Follow-up: Why no chat? An activity feed covers updates and keeps scope small.

Architecture

★ Walk me through the architecture.

A React PWA talks to Supabase. Inside the app, UI screens call feature modules, which use pure logic from packages/core and a local Dexie database with an outbox. Supabase provides Postgres with Row Level Security, Auth, Storage and Realtime. There is no custom server.

Follow-up: Why keep logic in a separate package? It has no UI or network dependency, so it is easy to test fully and cannot be bypassed by screen code (rule ARC-001).

★ How does offline work?

Every write goes to Dexie first and into an ordered outbox with a client-generated id. The sync engine replays the outbox when online. Operations are idempotent, so a retry cannot duplicate a row. Pulls fetch rows changed since the last pull, including tombstones.

Follow-up: What if the replay fails? The operation stays visible with a retry button and is never dropped silently (SYN-005).

Why Supabase and not a custom backend?

Free tier, built-in auth and realtime, and Row Level Security puts the access rules in the database where they cannot be skipped. A custom server would add cost and operations work.

Follow-up: Any downside? Free projects pause after about a week idle, so a keep-alive workflow pings them.

Why a PWA plus Capacitor?

One TypeScript codebase serves browsers and an Android APK. Capacitor adds native share, filesystem and notifications. iOS users install the PWA.

Follow-up: Why no React Native? It would mean a second codebase and UI layer.

Money and algorithms

★ Why integers in paise instead of floats?

Floats cannot represent most decimals exactly, so shares drift by fractions and balances stop summing to zero. Integers make every total exact. Rates use basis points or decimal strings, and large intermediate products use BigInt.

Follow-up: How do you split ₹100 among three? allocate gives 3334, 3333, 3333 paise in a deterministic order; the sum is exactly 10000.

★ Explain the fair tax algorithm.

First spread any discount over the items in proportion to their price. Then split each item among its assignees by weight, tracking tax class. Each person's item total becomes their weight for sharing service charge, tip and tax. A class-specific tax, such as alcohol tax, uses only that class. Charges marked "equal" use weight 1 per participant. The sum of owed amounts equals items plus signed charges exactly.

Follow-up: What if the printed total differs? Saving is blocked until it matches; under ₹5 the form offers a one-tap round-off line.

★ How does debt simplification work and is it optimal?

Compute each member's net balance, then repeatedly match the largest debtor with the largest creditor, settling the smaller of the two. This yields at most n − 1 transfers. It is a greedy method, not guaranteed to give the minimum number of transfers in every case (that problem is NP-hard), but it is deterministic and good in practice.

Follow-up: Can users turn it off? Yes, a group setting shows pairwise amounts instead.

How do you handle multiple currencies?

The user enters a rate; the base total is the total times the rate, rounded half up, and base shares come from allocate. Balances use base amounts only. Fetching a rate from Frankfurter is optional and failure falls back to manual entry.

Follow-up: Why not auto-convert always? Network may be absent and rates differ from what the card charged.

How does the UPI settle-up avoid false payments?

The app opens the UPI link, and when the user returns it asks "Did the payment go through?". It records the settlement only on confirmation, because it cannot see the bank result.

Follow-up: Could someone lie? Yes, as with cash; any settlement can be deleted by members with write access.

Sync and conflicts

★ What happens when two people edit the same expense?

The server compares base_version. A stale write is rejected with VERSION_CONFLICT. The client keeps the local draft and opens a "Review changes" screen with "Keep theirs" or "Apply mine on top".

Follow-up: Why not last-write-wins for expenses? It would silently lose money data. Other tables use last-write-wins because edits are low stakes.

Why does the server not recompute shares?

The core engine is the single source of the arithmetic (ARC-002). The RPC only verifies that payers and shares sum to the total, which catches tampering or bugs without duplicating logic in SQL.

Follow-up: Is that a trust problem? Only group members with write access can call it, and the sums are enforced.

How are deletions synced?

Soft deletes. Deleted rows stay as tombstones, so every device learns of the deletion on its next pull.

Follow-up: Are tombstones kept forever? They are small; cleanup is a possible future job.

Security and privacy

★ How do you stop one group seeing another's data?

Row Level Security on every table, with policies based on group membership. 806 pgTAP assertions test the isolation. Writes go through RPCs that check can_write.

Follow-up: What about storage files? Paths start with the group id, and URLs are signed and expire within an hour.

★ How is face data handled?

Opt-in only. A member consents, takes a selfie, and the device stores a numeric fingerprint, not an image. Matching runs on the uploader's device against consenting members only. Unmatched faces are discarded at once. Withdrawal deletes the fingerprint and all automatic tags. Non-consenting members can never be auto-tagged.

Follow-up: What if the model changes? Fingerprints from different model_ids are never compared; the member re-enrols.

What happens to data when a user deletes their account?

Profile and face data are removed. In each group the member becomes a "Former member" placeholder so expenses and balances stay correct. A single Edge Function with the service key, stored only as a secret, deletes the auth user.

Follow-up: Photos? The user chooses to keep or delete them.

How do you protect secrets?

No secrets or .env files in git. The client only has the public anon key. The service-role key exists only as a Supabase secret.

Follow-up: What if the anon key leaks? It is public by design; Row Level Security is what protects data.

Photos, OCR and Instagram

How do photos sort themselves into days and places?

EXIF time is bucketed into trip days in the group's timezone, and optional EXIF location gives the place. Both are optional consents; the album works without them.

Follow-up: No EXIF? The photo falls back to upload time and can be edited.

★ Why share through the share sheet instead of posting to Instagram?

The official API only works with Business or Creator accounts, and the personal-account API ended on 4 December 2024. Asking users for Instagram credentials would be unsafe. So Chalo renders the image or video and hands it to the phone's share sheet, with a download and copied caption as a fallback.

Follow-up: How are reels made? Canvas drawing recorded with MediaRecorder; FFmpeg WebAssembly converts WebM to MP4 only if needed.

How does receipt scanning work and why is it safe?

tesseract.js runs in the browser, so the photo never leaves the device. It produces an editable draft in the itemised form, and nothing saves without the user's review.

Follow-up: Accuracy? Unverified on crumpled receipts; that is why review is mandatory.

Testing and CI

★ How do you know the money maths is right?

Three layers: normative test vectors from Appendix A that must match to the paisa, property tests with fast-check for invariants (sums, non-negativity, order independence), and Playwright tests that reproduce the restaurant bills through the UI. Core has 100% line coverage.

Follow-up: What if a vector looked wrong? The working agreement says stop and ask, not edit it.

What does CI run?

Lint, typecheck, unit and property tests, SQL tests on a local Supabase stack, and the build. Merging needs green checks.

Follow-up: What was flaky? Offline browser tests; fixed by waiting for a ready signal before disconnecting.

What is not covered by automated tests?

Real-phone behaviour: Android share sheet, local notifications, music app links, face accuracy on real faces, receipt OCR on real receipts. These are recorded manual checks.

Follow-up: Is a P0 allowed without a test? No: it needs a test or a dated manual result.

Process

★ What is spec-driven development and how did you apply it?

Write the contract first, then build to it. Each requirement has an ID, a priority and a pass/fail criterion; milestones have a Definition of Done. Commits and tests carry the IDs, and a traceability test checks them against the spec. Decisions and spec changes are logged in separate files.

Follow-up: Did the spec change? Yes, through SPEC_CHANGES.md, from v0.1 to v0.2 and later, with the reason recorded.

★ How did you use AI in the build?

Claude Code implemented milestones under a working agreement in CLAUDE.md: plan first, tests first for the core, small commits, stop-and-ask rules for cost, privacy and destructive actions. I set the scope, approved decisions and ran the manual checks. (Edit this answer to match your own account.)

Follow-up: How did you verify its output? Tests, the Definition of Done on staging, and reading the diffs.

Why one branch and pull request per milestone?

It keeps review small, makes each milestone tag a clean rollback point, and ties history to the plan.

Follow-up: Any force pushes? Never on main.

Failure scenarios

★ The phone is offline for two days. What happens?

Everything keeps working from Dexie; new expenses and photo metadata queue in the outbox and the status shows "N pending". Bookings opened once online stay available. On reconnect the outbox drains and the app pulls changes. Conflicting expense edits go to the review screen.

Follow-up: Photo uploads offline? They wait for a connection and run one at a time.

Supabase free project gets paused. What do you do?

Prevention is the keep-alive workflow. If it happens, restore from the dashboard; docs/BACKUP.md describes the backup routine. Local data is still in each device's Dexie store.

Follow-up: Could data be lost? Unsynced local writes survive in the outbox until sent.

A face is tagged wrongly. What now?

Any member can remove a tag, and people can always remove tags of themselves. Matches close to the threshold are marked "check this" for one-tap confirmation. The threshold can be tuned with the debug screen.

Follow-up: Can someone be tagged without consent? No; without consent there is no fingerprint to match.

What would you do with another month?

Tune the face threshold on real photos, run the legal privacy review, test on more real Android devices, add Hindi and other languages, and consider a native iOS build.

Follow-up: What would you cut? The stretch items, never the P0 money and privacy work.
